기여자가 많으면
이슈는 더 빨리 처리될까

CNCF 클라우드 네이티브 오픈소스 10개 프로젝트, 12개월치 데이터로 검증한 오픈소스 커뮤니티의 오래된 통념.

작성자 김상혁 작성일 2026-09-16 표본 10개 프로젝트 × 12개월 (n=119)
가설 기각

“활성 기여자 수가 많을수록 이슈 처리 시간이 짧다”는 가설은 이번 표본에서 지지되지 않았다. 전체적으로는 상관관계가 거의 없었고(r=-0.041), 극단값을 제외하면 오히려 반대 방향(양의 상관, r=+0.226, p=0.017)이 유의하게 나타났다.

Abstract

초록

오픈소스 소프트웨어 운영에서는 “기여자가 많을수록 이슈나 버그가 더 빨리 해결된다”는 통념이 널리 퍼져 있다. 본 연구는 이 통념을 CNCF(Cloud Native Computing Foundation) 소속 클라우드 네이티브 프로젝트 10개(Envoy, Prometheus, containerd, etcd, Vitess, CoreDNS, Helm, TiKV, Linkerd, Rook)를 대상으로 실증적으로 검증했다.

GitHub REST API를 통해 각 프로젝트의 최근 12개월간 월별 활성 기여자 수와 이슈 평균 처리 시간을 수집했으며(n=120, 결측 1건 제외 시 119건), 피어슨 상관분석과 세 가지 강건성 검증(로그 변환, 이상치 제외, 프로젝트 단위 집계)을 수행했다. 분석 결과 전체 표본에서는 유의한 상관관계가 나타나지 않았고, 기여자 수가 유독 많은 Envoy를 제외하면 오히려 기여자 수가 많을수록 처리 시간이 길어지는 유의한 양의 상관이 확인되었다. 이는 원래 가설과 반대되는 결과로, 조율 비용 증가 등 대안적 설명이 필요함을 시사한다.

1

서론

오픈소스 소프트웨어 커뮤니티에는 “눈이 충분히 많으면 버그는 얕아진다(Linus's Law)”는 유명한 격언이 있다. 이 격언은 기여자·리뷰어 수가 많을수록 문제 발견과 해결이 빨라진다는 믿음으로 이어져, 실무에서는 종종 기여자 수나 스타 수를 프로젝트 “건강성”의 대리 지표로 사용한다. 그러나 이 관계가 실제 데이터로 얼마나 뒷받침되는지는 프로젝트마다 다르게 보고되어 왔다.

선행 연구를 보면, Nguyen Duc 외(2011)는 이해관계자 유형과 협업 정도가 OSS 이슈 처리 시간에 영향을 준다는 직접적 근거를 제시했다. 반면 Ajibode 외(2023)는 6개 머신러닝 라이브러리 중 단 1개(Keras)에서만 기여자 수와 이슈 처리 기간 사이 상관관계를 발견했고, 나머지 4개에서는 뚜렷한 관계가 없었다. Eiroa-Lledo 외(2023)는 프로젝트 규모·성숙도 같은 프로젝트 특성이 버그 해결 시간에 영향을 준다는 일반적 근거를 제공했으며, Sülün 외(2024)는 이슈 템플릿 같은 운영 관행만으로도 해결 시간이 크게(381일→103일) 달라질 수 있음을 보여, 기여자 수 외의 교란 변수가 존재함을 경고했다.

이러한 선행 연구들은 대부분 개별 언어 생태계나 일반 오픈소스 저장소를 대상으로 했으며, 클라우드 네이티브 인프라를 다루는 CNCF 생태계에 한정해 “기여자 수 → 이슈 처리 속도” 관계를 검증한 연구는 확인되지 않았다. CNCF는 DevStats라는 공개 데이터 포털을 공식 운영하며 기여자·이슈 지표를 투명하게 공개하고 있어, 이 생태계를 대상으로 한 검증은 실행 가능하면서도 기존 연구의 공백을 채울 수 있는 주제다.

가설

CNCF 오픈소스 프로젝트는 활성 기여자 수가 많을수록, 이슈가 열린 시점부터 닫히는 시점까지 걸리는 평균 처리 시간이 짧다.

2

방법

2.1 분석 대상

CNCF Graduated 등급 프로젝트 중, Kubernetes처럼 여러 저장소·SIG 구조로 나뉘어 집계가 복잡한 경우를 제외하고, 단일 대표 저장소를 가진 프로젝트 10개를 규모가 다양하도록 선정했다: envoyproxy/envoy, prometheus/prometheus, containerd/containerd, etcd-io/etcd, vitessio/vitess, coredns/coredns, helm/helm, tikv/tikv, linkerd/linkerd2, rook/rook.

2.2 변수 정의 및 데이터 출처

  • 활성 기여자 수 — 해당 월에 최소 1회 이상 커밋을 남긴 고유 작성자 수 (GitHub REST API 저장소 커밋 목록)
  • 이슈 평균 처리 시간 — 해당 월에 닫힌 이슈들의 (닫힌 시각 − 생성 시각), 일 단위 평균 (GitHub Search Issues API)
  • 관측 기간 — 2025-09 ~ 2026-08 (최근 12개월)
  • 데이터 출처 — GitHub REST API(api.github.com), 2026년 9월 15일~16일에 실제 호출하여 수집

속도 제한(rate limit)에 대응하는 재시도·백오프·재개 로직을 갖춘 자체 스크립트로 자동 수집했다. 최종 표본 크기는 10개 프로젝트 × 12개월 = 120개 관측치이며, 이 중 1개(CoreDNS, 2026년 2월)는 그 달에 닫힌 이슈가 0건이어서 상관분석에서 제외했다(유효 n=119). 전체 수집에 앞서 CoreDNS 저장소 2025년 1월 한 달치만으로 스크립트 로직을 시험 실행해 정상 산출을 확인한 뒤 전체 수집을 진행했다.

2.3 분석 방법 및 가설 기각 기준

피어슨 상관계수(r)와 t-근사 유의확률(p)을 계산하고, 세 가지 강건성 검증을 추가했다: 로그 변환, 이상치(Envoy) 제외 재계산, 프로젝트별 평균 집계. 사전에 정한 기각 기준은 “p≥0.05이거나, 부호가 가설이 예측한 음(−)의 방향이 아닌 경우”였다.

2.4 바뀐 조건과 고정한 조건

  • 바뀐 조건 — 프로젝트(10개), 관측 월(12개월)
  • 고정한 조건 — 변수의 조작적 정의, 데이터 출처, 관측 기간의 길이
3

결과

전체 표본(n=119)에서는 통계적으로 유의한 상관관계가 나타나지 않았다. 프로젝트별로 보면 4개는 가설이 예측한 음의 상관 방향을 보였으나 모두 유의하지 않았고(p>0.4), 6개는 가설과 반대인 양의 상관을 보였다 — 그중 CoreDNS는 p<0.001로 강하고 뚜렷하게 유의했다.

4

논의

4.1 가설 검증 결과

가설은 지지되지 않았다. 극단값(Envoy)을 제외하면 통계적으로 유의한 반대 방향의 관계가 나타났고, 유일하게 강하게 유의했던 CoreDNS 역시 반대 방향이었다. 데이터에 맞춰 가설을 수정하지 않고, 원래 문장 그대로 기각하는 것이 타당하다고 판단했다.

4.2 반대 방향으로 나타난 이유 — 대안 설명

  1. 운영 관행 차이 — Sülün 외(2024)가 보였듯 이슈 템플릿·트리아지 체계가 처리 시간을 크게 좌우할 수 있는데, 이번 연구는 이 변수를 통제하지 못했다. 기여자가 늘수록 조율 비용(coordination overhead)이 함께 늘었을 가능성이 있다.
  2. 프로젝트 규모·복잡도 — Eiroa-Lledo 외(2023)가 지적한 대로, Envoy처럼 기여자 수 자체가 큰 프로젝트는 기업 소속 상근 인력 비중이 높아 “기여자 수”의 의미가 다른 프로젝트와 다를 수 있다.
  3. 관계 자체가 프로젝트마다 다름 — Ajibode 외(2023)가 6개 라이브러리 중 1개에서만 상관관계를 발견했듯, 이번에도 10개 중 1개(CoreDNS)만 강하게 유의했다. “기여자 수 하나로 설명되는 보편 법칙은 없다”는 결론과 일치한다.
  4. 측정 방식의 한계 — 활성 기여자 수를 커밋 작성자 수로 근사해, 봇 계정·일회성 기여자가 섞였을 수 있다.

4.3 한계

  • CNCF 소속 10개 프로젝트·12개월로 제한되어 오픈소스 전반으로 일반화할 수 없다.
  • “활성 기여자 수”는 커밋 작성자 수의 근사치이며 봇 계정을 구분하지 않았다.
  • “닫힌 이슈”에는 해결된 것과 wontfix/stale로 종료된 것이 섞여 있다.
  • 상관관계 분석이므로 인과관계나 역인과 가능성을 배제할 수 없다.

4.4 결론

이번 표본(n=119)에서는 활성 기여자 수와 이슈 평균 처리 시간 사이에 유의미한 음의 상관관계가 나타나지 않았다. 오히려 CoreDNS처럼 기여자가 많을수록 처리 시간이 길어지는 강한 반대 방향의 사례가 있었고, 이상치인 Envoy를 제외하면 전체적으로도 유의한 양의 상관이 나타났다. 따라서 원래 가설은 이 표본에서는 기각되며, 일부 프로젝트에서는 기여자 증가가 조율 비용 증가로 이어져 처리를 늦출 수 있다는 정반대의 가능성이 시사된다. 이 결론은 이번에 수집한 10개 CNCF 프로젝트·12개월 데이터에 한정된다.

A

부록. 연구 설계 및 진행 과정

A.1 관심 분야와 후보 주제

관심 분야는 네트워크 보안, 프론트엔드/백엔드 개발, 클라우드 엔지니어링이었다. 이 안에서 AI와 함께 공개 데이터로 검증 가능한 후보 주제 10개를 브레인스토밍한 뒤, 다음 3개로 좁혔다.

  • 후보 A — 오픈소스 인기도(스타 수)가 취약점 대응 속도에 영향을 준다 (GitHub Advisory DB 기반)
  • 후보 B — 네트워크 트래픽 특성이 공격 트래픽 분류와 관련 있다 (CICIDS2017/NSL-KDD 기반)
  • 후보 C (채택) — CNCF 프로젝트의 활성 기여자 수가 이슈 처리 속도에 영향을 준다 (CNCF DevStats/GitHub API 기반)

A.2 후보를 접은 이유와 최종 선택 이유

후보 A는 두 API를 직접 매칭해야 해서 데이터 정제 작업량이 가장 크고 완주 위험이 있어 접었다. 후보 B는 데이터가 이미 라벨링돼 실행은 쉬웠지만 표준 분류 문제에 가까워 참신성이 낮다고 판단해 접었다. 후보 C는 클라우드 엔지니어링 관심사를 직접 반영하면서, CNCF가 공식 운영하는 DevStats라는 목적에 맞는 공개 포털이 있어 신뢰도가 가장 높다고 판단해 채택했다.

A.3 AI와 가설을 다듬은 과정

① 관심 분야 제시 → ② AI가 공개 데이터 기반 후보 10개 제안 → ③ 그중 2개를 직접 지목하고 클라우드 주제 1개 추가 요청 → ④ AI가 CNCF DevStats 기반 주제를 제안 → ⑤ 가설 문장·측정 방법·반증 조건을 구체화한 뒤 최종 확정.

A.4 데이터 수집 방식을 도중에 바꾼 이유

원래 계획은 DevStats 대시보드에서 프로젝트별로 수동 다운로드하는 것이었으나, 100회 넘는 수작업이 필요해 GitHub REST API 자동 스크립트 방식으로 바꿨다. DevStats에서 확인한 “이 지표가 실제로 존재하고 의미 있다”는 사실은 유지하되, 수집 경로만 재현 가능한 스크립트로 바꾼 것이다.

A.5 참고문헌 출처 확인 방법

각 논문 제목을 웹 검색해 학술 출판사(Springer, MDPI, ACM) 또는 arXiv의 원문 페이지·DOI가 실제로 존재함을 확인했으며, 4개 URL 모두 로그인·계정 생성 없이 새 창에서 열리는 것을 확인했다.

02데이터 수집 방법 전환 — AI가 GitHub API 스크립트 방식을 제안했지만, 토큰 발급과 실제 실행은 보안을 위해 내가 직접 진행했다.
03결과 해석 — 통계 계산은 AI가 했지만, 반대로 나온 결과를 가설에 맞춰 짜맞추지 않고 있는 그대로 “기각”으로 받아들이기로 한 것은 내 판단이다.
